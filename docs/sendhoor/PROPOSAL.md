# Sendhoor Holidays: Proposed Architecture, Folder Structure, and Schema

Status: **awaiting approval.** No application code will be written until this is approved.

## 0. Assumptions (please confirm or correct)

The brief left these as placeholders. I chose defaults so the proposal is complete:

| Item | Assumed | Why it matters |
|---|---|---|
| Services | (1) Tour packages, (2) flight and hotel **booking requests** (no live airline or hotel inventory), (3) custom trip requests | Drives the `request_type` enum and the package model |
| Currency | INR, stored per record as a 3-letter code | Amounts are stored as integer minor units (paise), never floats |
| Payments | No gateway in v1. The owner records manual payments. `payments` is a placeholder table | Avoids gateway onboarding before the business is live |
| Language | English, all UI text in `client/src/i18n/en.json` keyed by message ID | Makes adding languages later a translation task, not a refactor |
| Hosting | Frontend and API on the same registrable domain (for example `sendhoor.com` and `api.sendhoor.com`) | Required for `SameSite=Strict` cookies to be sent by the browser to the API |

## 1. Architecture

```
Browser (React + Vite + Tailwind + Framer Motion)
   │  HTTPS only, httpOnly cookies (access + refresh), X-CSRF-Token header
   ▼
Express API (TypeScript) ── Helmet, CORS allowlist, rate limits, Zod validation
   │
   ├── PostgreSQL (via Prisma; migrations only)
   ├── Object storage (S3-compatible; local disk in dev) for package images
   └── Email provider (verification, reset, booking updates)
```

**Backend choice: Express.** The brief lists Express first, the API surface is modest (about 40 endpoints), and Express with Zod gives explicit control over each security middleware. NestJS would be the better fit if you expect a large team or many more modules; it adds decorators, DI, and a larger learning curve for a small team.

**Single deployable.** One API process serves JSON. The frontend is a static build on a CDN or Nginx. No microservices.

Notes:
- `features/` keeps logic out of `pages/`, so pages stay thin and tests are easier.
- Each server module keeps `service` (business rules) apart from `controller` (HTTP), so authorization checks sit in services where object-level rules belong.
- `prisma/migrations` is generated. All schema changes go through `prisma migrate dev` and are committed.

## 3. Database Schema

## 4. Security Design (summary; full list in docs/SECURITY.md after build)

| Area | Decision |
|---|---|
| Passwords | argon2id (memory 19 MiB, 2 iterations, parallelism 1, or OWASP defaults). Min 12 characters; checked against a breached-password list (k-anonymity API) |
| Lockout | 5 failed attempts per account: 15-minute lock. Per-IP progressive delay after 10 failures in 10 minutes. Same generic message for unknown email and wrong password |
| Tokens | Access JWT 15 min. Refresh token 7 days, opaque, rotated on each use, stored as SHA-256 hash. Reuse revokes the family |
| Cookies | `access_token` and `refresh_token`: `HttpOnly; Secure; SameSite=Strict; Path=/` (refresh scoped to `/api/auth`). CSRF cookie readable by JS, matched against `X-CSRF-Token` |
| CSRF | Double-submit token on every state-changing request from a cookie session |
| RBAC | `authorize(roles, permissions)` on every protected route. OWNER bypasses; STAFF needs the listed permission; CLIENT limited to own resources |
| IDOR | Services load resources with `where: { id, userId }` for clients. Tests cover cross-user access for every client-facing endpoint |
| Rate limits | Login 5/15 min per IP+account; register 5/hour per IP; forgot password 3/hour per email; contact form 3/hour per IP; global 300/min per IP |
| Validation | Zod on every route for body, query, and params. Unknown keys rejected. JSON body limit 100 KB |
| XSS | React escapes by default. `description_html` sanitized on server with an allowlist (DOMPurify on server via jsdom, or sanitize-html) and again on render. No `dangerouslySetInnerHTML` except sanitized HTML |
| SQL injection | Prisma only. Any `$queryRaw` must use tagged templates; a lint rule bans `$queryRawUnsafe` |
| Uploads | Max 5 MB, max 10 files per package. MIME check against allowlist plus magic-byte check (file-type). Re-encode with sharp, which strips EXIF and metadata. Random storage key. Served from object storage or a static path that does not execute files |
| Headers | Helmet: `Content-Security-Policy` (default-src 'self'; img-src 'self' https: data:; no inline scripts), `Strict-Transport-Security` (1 year, includeSubDomains), `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin` |
| CORS | Allowlist = frontend origin only, `credentials: true` |
| Tokens in email | Verification and reset: 32-byte random, hashed in DB, single use, expire in 24 h and 30 min. Reset response is always 202 (no account enumeration) |
| Audit | Login success and failure, lockouts, role and permission changes, booking status changes, client disables, package and image deletions |
| Errors | Client gets `{ error: { code, message, requestId } }`. Stack traces only in logs |
| Logging | pino with redaction for `password`, `token`, `cookie`, `authorization` |
| Secrets | Env only. `.env.example` with names and placeholders. Startup fails if `JWT_SECRET` is shorter than 32 bytes or still equals an example value |
| Dependencies | Lockfile committed. `npm audit --audit-level=high` in CI. Dependabot enabled |
| Transport | HTTPS only; HTTP redirects to HTTPS at the edge; HSTS preload-ready once the domain is confirmed |
| Owner seed | Owner email and initial password come from env. Forced password change on first login |

**Known tradeoffs to confirm:**
- Access tokens are JWT (stateless). A disabled account keeps working for up to 15 minutes until the token expires. Mitigation: the auth middleware checks `is_active` on each request, which costs one indexed lookup. I recommend the check; it is the default in this plan.
- Uploads are processed on the API server (sharp). Simple and secure, but large batches block the event loop. Mitigation: a single-file limit and a queue later if needed.
- Manual payments only in v1. No money moves through the site, so PCI scope is zero.
